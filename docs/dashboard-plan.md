# Пульт управления MoneyForesight — план

Цель: не открывать вручную графики каждой монеты на каждом таймфрейме, а видеть одну таблицу и
получать уведомление, когда на монете случилось что-то важное.

**Решения (28 октября 2026):** считаем оба вида пробития; сначала HTML-страница, потом Telegram;
стартовый список — топ-20 монет по капитализации (`SYMBOLS` в [`mf_config.py`](../mf_config.py)).

## Что именно считать «линией, которая меняет цвета»

Это **Rainbow MA** ([`MoneyForesight_v3.pine`](../MoneyForesight_v3.pine), блок «3 · RAINBOW MA»).
Цвет задаёт число `rbHeat` от 0 до 1 — это RSI(50), посчитанный от самой линии:

| `rbHeat` | Цвет | Смысл |
|---|---|---|
| 0.0 | ярко-красный | сильное падение |
| 0.5 | оранжевый | нейтраль / флэт |
| 1.0 | ярко-зелёный | сильный рост |

**Что важно знать до начала.** Линия сильно запаздывает: вес текущей свечи равен нулю, а центр
весов лежит примерно на 24–25 свечей назад. Поэтому цвет — это **медленный режим тренда, а не
прогноз**. Из-за такого запаздывания на недельном таймфрейме цвет должен меняться редко
(порядка месяцев), на дневном — заметно чаще, но тоже с опозданием. Это оценка по формуле, на
истории я её ещё не измерял; измерим на этапе 1. Для пульта это нормально: старшие таймфреймы
дают фон, младшие — тайминг.

**«Пробитие» бывает двух видов, и они разные по скорости:**

1. **Цена пересекла линию.** Срабатывает раньше, но шумнее.
2. **Цвет линии перешёл через 0.5** (из красно-оранжевой половины в зелёную или обратно).
   Срабатывает позже, зато надёжнее.

Пульт будет считать оба, а какой из них лучше — решим по истории (этап 3), а не на глаз.

## Как это будет работать

```
свечи биржи (публичные, без ключей)
        │
        ▼
ядро расчёта: Rainbow, Chandelier, ADX/DMI, MACD  ← на каждом таймфрейме отдельно
        │
        ▼
состояние ячейки «монета × таймфрейм»: цвет, цена выше/ниже линии, свежесть пробоя
        │
        ▼
сведение по таймфреймам: старший задаёт фон, младший — тайминг → счёт согласованности
        │
        ├──► таблица пульта (HTML)
        └──► события → уведомление (Telegram)
```

Макет того, что вы увидите (цифры и цвета вымышлены, живых данных пока нет):

| Монета | 1W | 1D | 4H | 1H | 30m | Счёт | Что случилось |
|---|---|---|---|---|---|---|---|
| BTC | 🟩 ↑ | 🟩 ↑ | 🟨 ↑ новый | 🟥 ↓ | 🟥 ↓ | +48 | 4H: цвет линии пересёк 0.5 вверх |
| ETH | 🟧 ↓ | 🟩 ↑ новый | 🟩 ↑ | 🟩 ↑ | 🟩 ↑ | +35 | 1D: цена пробила линию вверх |

Ячейка = цвет линии (как в TradingView) + стрелка «цена выше/ниже линии» + метка «новый», если
пробитие случилось в последние N свечей этого таймфрейма.

**Счёт согласованности** — взвешенная сумма «голосов» таймфреймов от −100 до +100. Веса по
умолчанию отражают вашу логику каскада: 1W — 5, 1D — 4, 4H — 3, 1H — 2, 30m — 1. Веса и набор
таймфреймов лежат в конфиге, их можно менять.

## «Вероятность» — три честных уровня

Число «вероятность роста 70%» без проверки на истории — просто красивая цифра. Поэтому по шагам:

1. **Счёт согласованности** (сразу). Это *не* вероятность, и в пульте так и подписано.
2. **Эмпирическая вероятность** (этап 3). По всей истории считаем: когда была такая же
   конфигурация таймфреймов, как часто цена потом шла вверх. В пульте выглядит так:
   «в такой конфигурации раньше рост в 58% случаев, n = 214, доверительный интервал 51–65%,
   базовая частота 52%». Всегда показываем `n`, интервал и базу для сравнения. Проверка —
   на периоде, который не участвовал в подсчёте (walk-forward).
3. **Решение по итогам.** Если на проверочном периоде преимущества над базовой частотой нет,
   пульт честно остаётся «картой режимов», а слово «вероятность» не используем.

Почему осторожность оправдана: по [README](../README.md) стратегия на 1h и младше убыточна
(PF 0.4–0.9), а на 4h PF 1.24 получен на тех же данных, на которых подбирался фильтр.

## Данные, «API-ключи» и другие индикаторы

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Пересчёт в Python** (основной) | Свечи с публичного API биржи, индикаторы считаем сами. В репозитории уже есть порт логики ([`backtest.py`](../backtest.py)) и тесты на совпадение с Pine | Ключи не нужны, любое число монет и таймфреймов, нет лимитов TradingView | Нужно сверить числа с TradingView (проверка совпадения в этапе 1) |
| B. Алерты TradingView → вебхук | Индикатор шлёт JSON на наш адрес | Работает с любым, в том числе закрытым индикатором | Нужен платный тариф; один алерт на монету и таймфрейм; лимит числа алертов |
| C. Неофициальные библиотеки, выгружающие данные из TradingView | — | — | Нарушает правила сервиса, ломается без предупреждения. **Не берём** |

Про ключи: у TradingView нет публичного API, который отдаёт значения индикаторов. Биржевые свечи
и данные по фьючерсам (фандинг, открытый интерес, соотношение лонгов и шортов) лежат в
публичных эндпоинтах Binance без ключей. Ключи понадобятся только для Telegram-бота (токен от
BotFather) и, возможно, для CoinGecko. Хранить их будем в переменных окружения, не в репозитории.

Любой стандартный индикатор (RSI, MACD, Supertrend, Ichimoku, Bollinger) можно пересчитать в
Python, поэтому «добавить ещё индикаторы» = добавить модуль. Только закрытые индикаторы по
приглашению можно подключить исключительно через алерты (вариант B).

**Модули голосов.** Каждый модуль для пары «монета × таймфрейм» возвращает значение от −1 до +1
и короткую подпись. Ядро — Rainbow. Дальше подключаем по одному: Chandelier, ADX/MACD (уже есть
в коде), фандинг и открытый интерес, индекс страха и жадности.

## Этапы

Каждый этап заканчивается тем, что можно запустить и проверить.

**Этап 0 — решения и доступ.** Решения приняты (см. выше). Доступ к биржевому API: из этой
облачной среды сеть закрыта (см. «Риски»), поэтому живые данные проверяются у вас.

**Этап 1 — ядро и сканер.** Код написан и проверен на синтетических данных; на живых данных
и в сверке с TradingView ещё не проверен.
- [x] Расчёт индикаторов вынесен из `backtest.py` в [`mf_core.py`](../mf_core.py). Результаты
  бэктеста не изменились: вывод `prepare()` и `run()` на 48 прогонах сравнён с версией до выноса
  побайтово, прежние 36 тестов зелёные.
- [x] Состояние Rainbow `rainbow_state()`: тепло, корзина цвета, цена выше/ниже линии, сколько
  свечей назад произошло каждое из двух пробитий, признак «свежее», охлаждение тепла за 3 свечи.
  Считает только по барам до проверяемого, будущего не касается (есть тест на это).
- [x] [`scan.py`](../scan.py): `python3 scan.py` печатает таблицу «монета × таймфрейм» и список
  свежих пробитий; сбой одной монеты не роняет обход.
- [ ] **Запуск на живых данных у вас** (команды ниже).
- [ ] **Сверка с TradingView:** `python3 scan.py BTCUSDT --tf 4h --inspect 5` печатает значение
  линии Rainbow на последних свечах; оно должно совпасть со значением «Rainbow MA» в окне данных
  графика `BINANCE:BTCUSDT` на тех же свечах. Тепло в TradingView числом не выводится, только
  цветом; если захотите сверять и его, добавим в индикатор скрытый вывод в окно данных.
- [ ] Измерить на истории, как часто меняется цвет на каждом таймфрейме (проверка оценки из
  начала документа).

Границы цветовых корзин (0.30 / 0.45 / 0.55 / 0.70) пока рабочие, не откалиброванные: уточним на
этапе 3.

**Этап 2 — пульт.**
- Сведение по таймфреймам со счётом согласованности. Настройки (монеты, таймфреймы, веса,
  пороги цветовых корзин) — в `mf_config.py`: Python-файл, а не TOML, чтобы не требовать
  Python 3.11+.
- `dashboard.py` собирает один HTML-файл с таблицей и лентой событий. Без сервера: открывается
  двойным кликом, обновляется запуском скрипта.

**Этап 3 — историческая калибровка.**
- Для каждой исторической свечи строим конфигурацию таймфреймов, используя **только закрытые**
  свечи старших таймфреймов, и считаем, куда ушла цена через N свечей.
- Таблица «конфигурация → частота роста, `n`, интервал, база», разбивка по периодам.
- Сравниваем оба вида «пробития» и подбираем пороги корзин (по обучающему периоду, проверяем
  на остальном).
- Итог: решение из пункта 3 раздела про вероятность.

**Этап 4 — уведомления.**
- Состояние прошлого запуска хранится в файле, уведомление уходит только при **смене**
  состояния, с паузой на пару «монета × таймфрейм × событие», чтобы не было спама.
- Telegram-бот. Только по закрытым свечам, как и сам индикатор.
- Запуск по расписанию: на вашем компьютере (cron) или в GitHub Actions.

**Этап 5 — расширения.** Фандинг и открытый интерес, индекс страха и жадности, версия
индикатора на Pine с таблицей по нескольким таймфреймам для визуальной сверки, вебхук-алерты.

## Риски

| Риск | Что делаем |
|---|---|
| Заглядывание в будущее на старших таймфреймах (берём ещё не закрытую недельную свечу) | Только закрытые свечи; отдельный тест на синтетических данных |
| Числа в Python расходятся с TradingView (разная длина истории, прогрев RSI/RMA) | Сверка по контрольным значениям; в README прогрев уже учтён (`WARMUP = 150`) |
| Подгонка весов и порогов под историю | Подбор на одном периоде, проверка на другом; не более 2–3 свободных параметров |
| Мало истории у молодых монет на недельке (нужно около 150 недель, то есть почти 3 года) | Ячейка показывает «н/д», в счёт не входит |
| Сеть облачной среды закрыта: биржи недоступны, живые данные здесь не проверить | Либо открыть домен в настройках среды, либо запускать сканер у вас; до этого опираемся на тесты с синтетическими данными и выдуманных цифр не рисуем |
| Лимиты API биржи | 20 монет × 5 таймфреймов = 100 запросов за обновление, кэш уже есть |

## Что нужно от вас

1. Запустить сканер у себя и показать вывод:
   ```bash
   python3 scan.py BTCUSDT ETHUSDT --tf 1d --tf 4h
   ```
   Если Binance недоступен из вашей страны: `MF_BINANCE_API=https://data-api.binance.vision python3 scan.py ...`
2. Для сверки: значение «Rainbow MA» из окна данных TradingView (`BINANCE:BTCUSDT`, 4h) на 2–3
   свечах плюс то, что покажет `--inspect 5` на тех же свечах.
3. Проверить список `SYMBOLS` в `mf_config.py`: рейтинг по капитализации я из облака проверить не
   мог, а наличие пар на Binance тоже.
4. Если хотите, чтобы я проверял всё на живых данных сам: открыть `api.binance.com` (или
   `data-api.binance.vision`) в сетевых настройках облачной среды.
